CMP 106 — Engineering Computing

Lesson 01 · Why engineers script

  • A script makes a calculation repeatable, inspectable and correctable. A spreadsheet hides its logic inside cells; a script states it in order, so a reviewer can find the mistake.
  • Anatomy of a calculation script: inputs at the top with units in the names or comments, the computation in clear steps mirroring how you would do it on paper, and output that states its units.
  • Write the calculation the way you would work it by hand, then let the machine repeat it without getting bored or careless.

Lesson 02 · Variables, types, and expressions

  • A type says what a value is — whole number, real number, text, true/false — and most beginner errors are really type errors wearing a disguise.
  • Floats tell the truth approximately. Never test two computed decimals for exact equality; compare their difference against a tolerance instead. This is the professional pattern, not a workaround.
  • Present numbers like an engineer: keep full precision through the computation, round only at output, and label the units every time.

Lesson 03 · Control flow

  • Decisions run if, elif, else: the first true branch wins, so the order of tests is part of the logic.
  • Repetition comes in two kinds — a for loop over a known collection, and a while loop that runs until a condition changes.
  • Guard clauses refuse bad input early. Rejecting a negative diameter at the top is worth more than any amount of careful arithmetic performed on it afterwards.

Lesson 04 · Functions

  • A function is a calculation with a name. One function should do one nameable thing.
  • Return, do not print. A function that returns its value can be composed into a larger calculation and tested; one that only prints is a dead end.
  • Scope means what happens inside a function stays inside it. Pass in what it needs rather than relying on values defined elsewhere.

Lesson 05 · Testing and debugging engineering code

  • Engineers test code because the dangerous failure is not a crash — it is a plausible-looking wrong number that goes into a report.
  • An assertion is a claim with teeth: it states what must be true and fails loudly at the exact moment the assumption breaks, instead of letting the error travel.
  • Exceptions let a program fail honestly rather than continuing on nonsense.
  • Pin a hand-checked case beside the function it certifies, so the code carries its own evidence.

Lesson 06 · Lists, dictionaries, and files

  • Lists hold ordered data; dictionaries hold records with named fields. Choose between them by how you intend to look things up — by position, or by name.
  • Files are where real data actually lives. Read it in rather than retyping it, and the retyping errors disappear with it.
  • The structure you choose early determines how painful every later question about the data will be.

Lesson 07 · Arrays and numerical work

  • The array idea: operate on the whole dataset at once instead of one element at a time. Shorter, faster, and far harder to get subtly wrong.
  • Reductions collapse many numbers into a few — sum, mean, maximum, standard deviation — and are most of what a data question actually asks for.
  • Masks ask questions of data ("which readings exceeded the limit?") and combine into compound questions, which is how filtering and counting are really done.

Lesson 08 · Plotting engineering data

  • A plot is an argument, not decoration. Axes get labels and units, or the argument cannot be checked.
  • Scales that reveal: a logarithmic axis turns exponential decay and power laws into straight lines, which is how you identify them by eye.
  • Sampling honesty: too few points invents a curve that was never in the data. The plot must not claim resolution the measurement did not have.

Lesson 09 · Curve fitting and interpolation

  • Two different questions. Interpolation honours every point and adds no opinion; fitting proposes a model and deliberately smooths over scatter. Each is wrong exactly where the other is right.
  • Linear interpolation between two table rows draws the chord between them — which is why property tables are published densely enough for that chord to be a good stand-in.
  • Least squares chooses the parameters that minimise the squared residuals, where a residual is measured minus predicted. \( R^2 \) reports how much of the variation the model accounts for.
  • A high-order polynomial can pass through every point exactly, residuals zero, and still swing wildly between them. Fitting every point is not the same as being right.

Lesson 10 · Small simulations

  • Most equations engineers actually meet are first-order rate equations with no closed form worth chasing, so they are marched forward numerically.
  • Euler's method is the honest workhorse: take the current rate, step forward, repeat. Crude, transparent, and enough to reason with.
  • When the step lies: stability. Too large a time step does not merely lose accuracy, it makes the answer diverge — the deviation grows each step instead of decaying.
  • Halve the step and re-run. If the answer moves, it had not converged, whatever the first plot looked like.

Lesson 11 · Project: a maintenance data mini-analysis

  • One project exercises the whole course: load real data, clean it, compute, plot, and report.
  • Cleaning is where the analysis is won or lost — mixed units, duplicated records and physically impossible values do more damage than any modelling choice made later.
  • KPIs need honest denominators. Availability, MTBF and MTTR mean nothing until you state what was counted and over what period.
  • Reproducibility is the deliverable: someone else, running your script on your data, must obtain your number. If they cannot, the number is an opinion.
